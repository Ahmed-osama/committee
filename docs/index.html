committee

A small AI-agent "company." Give it one goal; a Planner, Architect, Skeptic and friends hold a real, visible conversation to turn it into a stress-tested plan — with Linear as the eventual system of record, not a bespoke task database.

OVERVIEW & DIRECTION

Earlier on, this project built a full bespoke task-tracking/execution pipeline — a SQLite task state machine, git-worktree coding agents, a tick scheduler. That direction was abandoned on purpose. What the project is now: agents that converse to plan, out loud, where a human can watch and interject — with Linear as the task backend once it's connected, not another home-grown PM app.

DOMAIN MODEL

packages/core/src/domain defines the three core shapes. An Agent is a role + provider preference, not a running process. A Conversation is one goal being worked on. A Message is one turn — it carries a real intent (propose / challenge / clarify / agree / finalize / human / error) because planning is argumentative, not just structured status updates.

PLANNING SESSION

runPlanningSession (in conversation/planning-session.ts) is a round-robin loop, not a single agent's tool loop: each turn hands the full transcript to the next agent in order. Only the designated finalizer can end it, and only once the Skeptic has explicitly called agree — not just gone quiet — and has raised at least 2 real challenges first. That floor exists because on the first real run, the plan finalized before the Skeptic had said anything at all.

PROVIDER ROUTING

All roles share one canonical strength ordering (PROVIDER_STRENGTH_ORDER: anthropic → gemini → groq → deepseek → glm → openrouter → ollama). selectProvider walks it and returns the first entry that's configured, not rate-limited, and under the daily call/spend ceilings. rotateProviderOrder rotates the same list per role so the committee spreads across providers instead of every role fighting over the single strongest one.

PERSISTENCE

Everything lives in one SQLite database via Drizzle (persistence/schema.ts): agents, conversations, messages, and provider_calls — a single event log that doubles as both the rate-limit window (count rows in the last minute/day) and spend tracking (sum cost_usd), since both are just different queries over "what LLM calls actually happened."

ORCHESTRATOR PLUMBING

A running planning session is a plain in-process for loop with nothing else attached to it. injection-queue.ts and stop-registry.ts are the minimal shared mutable stores that let an HTTP request — "inject this text" / "stop this conversation" — reach a loop it isn't otherwise connected to. EventBus is the other direction: the loop publishes each message as it happens, and the web viewer's SSE endpoint just subscribes — a pure observer bolted on top, not something the engine needs to know exists.

EXECUTION TURNS

Once a plan is finalized (or the session otherwise ends), a human can type a command against the real codebase. runExecutionTurn (execution/execute-command.ts) is deliberately a different code path from the planning loop: one agent, real run_command / read_file / write_file tools, capped at 8 steps — action, not another round of debate.

FRONT DOORS: CLI & WEB

Two thin front ends share the same @committee/core engine. apps/cli (committee plan, transcript, serve, ...) drives it from a terminal. server/web-server.ts drives the same runPlanningSession from an HTTP API with an SSE stream, so you can watch a conversation live, inject messages, or stop it from a browser at localhost:3000.
