When a model narrates a tool call instead of making one

The Planner/Architect/Skeptic debate in packages/core/src/conversation/planning-session.ts was stalling: once the skeptic had genuinely agreed, the finalizer's only sanctioned move was to call finalize_plan, and the closing-phase prompt told the skeptic to call agree rather than raise new objections — but agents kept writing the literal words finalize_plan or "I agree" as plain text instead of invoking the actual tool. Offering a tool doesn't make the model use it; by default (toolChoice: 'auto' in the Vercel AI SDK's generateText) the model is still free to answer in prose, and once it's talked itself into treating the decision as already made, it has little incentive to also emit a structured call.

The fix, threaded through as a new toolChoice option on generateForAgent (packages/core/src/provider/generate-for-agent.ts), is to stop asking and start requiring: at the exact points where the caller already knows the tool call is the only valid next action, pass { type: 'tool', toolName: 'finalize_plan' } instead of leaving the tool set open-ended. This is a general rule for any tool-using agent loop — reserve free-form auto choice for turns where the model genuinely has options, and force a specific tool the moment your own code already knows there's exactly one legitimate action left. Leaving it to "the model should infer it's supposed to call this now" is exactly the gap that produces silent, budget- burning stalls.

Adding a new LLM provider without writing a new SDK client

Adding NVIDIA NIM and SambaNova to the provider roster (nvidia-nim-adapter.ts, sambanova-adapter.ts) took about ten lines each, not because those providers are simple, but because neither needed its own SDK. Both — like glm-adapter.ts, openrouter-adapter.ts, and ollama-adapter.ts before them — just point the Vercel AI SDK's createOpenAICompatible at a base URL and an API key:

const nvidiaNim = createOpenAICompatible({
  name: 'nvidia-nim',
  baseURL: 'https://integrate.api.nvidia.com/v1',
  apiKey: process.env.NVIDIA_API_KEY,
});

This works because most hosted-inference providers converged on the same wire format OpenAI's chat-completions API popularized — same request shape, same streaming event format — even when the model behind it is Llama or DeepSeek, not GPT anything. createOpenAICompatible is a generic client for that de-facto protocol, so "add a provider" becomes a config object instead of a bespoke integration, and every adapter in provider-registry.ts ends up satisfying the same ProviderAdapter interface (id + model(modelId)) regardless of which vendor is actually behind it — the rest of the codebase never has to know the difference.

The trade-off worth noting for next time: "wired" and "verified" are different claims. The nvidia adapter's own comment is explicit that its base URL and rate limits came from docs, not a live call — worth flagging in code whenever a new integration is added by research rather than by testing against a real key.

Reopening a finished loop: scope "did we already agree" to the new round

The web viewer's "regenerate" flow reopens a finalized planning conversation with fresh human feedback by calling runPlanningSession again, seeded with the old transcript via new initialTranscript/startTurn options in packages/core/src/conversation/planning-session.ts. That seeding created a subtle bug: the skeptic's earlier agree message from *before* the human's new feedback was still sitting in the transcript, and hasSkepticAgreed/countSkepticChallenges would see it and let the finalizer close the loop again immediately — with zero new debate on the thing the human just asked to change.

The fix is a one-line filter: const currentRound = transcript.filter((m) => m.turn >= startTurn), and every agreement/challenge check reads from currentRound instead of the full transcript. The general shape — "carry history forward for context, but scope the *decision* state to what's happened since this resumption" — comes up anywhere a stateful loop gets restarted with prior history attached: a chat session resumed with old messages, a retry loop that reuses a previous attempt's log. The seeded history should inform the prompt; it shouldn't count as evidence toward exit conditions that are supposed to reflect fresh work.

Pausing an async loop: poll a flag, don't block on a promise

runPlanningSession in packages/core/src/conversation/planning-session.ts needed a "pause" that a human can trigger mid-debate and later resume. The implementation isn't a Promise the pause handler resolves — it's a plain module-level registry (packages/core/src/orchestrator/pause-registry.ts) holding a set of paused conversation IDs, checked at the top of each turn:

if (isPaused?.(conversationId)) {
  onPausedChange?.(true);
  while (isPaused?.(conversationId)) {
    if (isStopRequested?.(conversationId)) return { finalized: false, turnsUsed: turn, stopped: true };
    await sleep(500);
  }
  onPausedChange?.(false);
}

This is a deliberate trade: a promise-based pause (resolve a stored "resume" promise from the HTTP handler) would react instantly and use zero CPU while waiting, but it couples the request handler to a live in-memory reference for that specific run — awkward once you also want stop to interrupt the same wait, and fragile across process boundaries. Polling a flag every 500ms is slightly wasteful and adds up to half a second of latency on resume, but it composes trivially: stop and pause are just two independent registries checked from the same loop, and either one can be flipped from any HTTP request with no shared promise plumbing. For a human-in-the-loop control this coarse (pause/resume happen on the order of seconds, not milliseconds), the simplicity is worth more than the theoretical responsiveness a promise would buy.

When a loop times out, force a degraded result instead of returning nothing

packages/core/src/conversation/planning-session.ts runs a fixed turn budget (maxTurns) for the Planner/Architect/Skeptic debate. Originally, if the skeptic never agreed before the budget ran out, the whole conversation just returned { finalized: false } — a potentially long, costly LLM conversation producing literally nothing usable. The fix adds two layers: a CLOSING_PHASE_FRACTION (75%) past which the skeptic is told to agree unless there's a genuinely critical objection, and — if the loop still exhausts every turn with no plan — one forced extra call that instructs the finalizer agent to call finalize_plan immediately from whatever was discussed, no further debate allowed.

The general pattern is worth naming: for any agent loop with a hard turn or time budget, decide up front what happens at the boundary. The naive default — let the budget run out and report failure — throws away all the (expensive) partial progress. Nudging behavior as the deadline approaches (the closing-phase prompt change) is cheap and often enough on its own; keeping a forced fallback call as a last resort means the *worst* case is "an imperfect plan from a real transcript," not "nothing, after burning the whole budget." The same shape shows up in agentic coding tools that force a summary/wrap-up turn when they're about to hit a context or step limit.

A shell script is a stronger guardrail than a prompt instruction

COM-9 added packages/skills/hooks/validate-linear-spec.sh, a PreToolUse hook wired in front of mcp__linear__save_issue and mcp__linear__save_project. It could have been "tell the agent in its system prompt not to file issues with an empty title" — but a system prompt is a request the model can still misread or skip under pressure from a long context. The hook instead runs as real code, outside the model's control: it reads the tool call's JSON off stdin, checks whether it's a create (no id field — updates like a bare status change are left alone) versus a genuinely empty title/name, and if so exits with code 2 and a JSON permissionDecision: "deny" payload that blocks the call outright before it ever reaches Linear.

The general lesson: for a narrow, mechanically-checkable invariant ("this field must be non-empty"), a deterministic pre-tool hook is strictly more reliable than instructing the model to self-police, because it can't be rationalized away mid-conversation. Save prompt instructions for judgment calls — hooks for anything you can express as a plain boolean check on the tool call itself.

Let a friction log decide what gets extracted, not a guess

Bootstrapping apps/digest as a second app on top of packages/core (COM-10) started from a guess: the two apps' session storage and provider routing looked similar enough to share an LLMClient/SessionStore abstraction. Instead of building that abstraction speculatively, the work logged real friction as it happened (apps/digest/FRICTION.md), then wrote down what actually diverged between the two apps' session and routing needs (packages/core/DIVERGENCE.md, COM-11) before touching shared code.

The friction log turned out to name only two things as genuinely duplicated with zero divergence: a provider-fallback function and a shared model-by-provider map. Those got extracted into packages/core (COM-12) — generateForAgent now retries across an agent's configured provider list on failure, marking each one down via markProviderDown so the next attempt steers around it, and apps/digest picked up that retry behavior for free just by calling the shared function instead of its own hand-rolled selectProvider → PROVIDER_REGISTRY → generateText chain. The bigger session/store abstraction the original task assumed was needed never got built — DIVERGENCE.md showed the two apps' needs aren't actually shaped alike yet. This is the "rule of three" instinct made procedural: write down where the duplication really is and isn't before reaching for a shared abstraction, so the abstraction boundary follows evidence instead of a first impression.

Further reading
  • Sandi Metz, "The Wrong Abstraction" — on the cost of extracting shared code too early and how to back out of it

Separating "what it does" from "what it's called"

The committee_plan MCP tool (apps/mcp-server/src/index.ts) used to seat a fixed six agents. The custom-roster addition lets a caller invent any seat titles and personas it wants ("Migration Skeptic", "Data Modeler") while still requiring each seat to declare one of a closed set of role values — planner, architect, skeptic, etc. That role is the only thing the round-robin loop actually reads to decide mechanics: which seats speak as challengers, and which single seat (a skeptic) gets veto power over finalizing the plan. name and persona are pure presentation, free-text, never inspected by the loop.

This is the same split as an enum-tagged union in code: a small closed set drives control flow, and an open string field carries whatever detail doesn't affect behavior. It's what makes free-form LLM-generated input (the calling agent invents seat names on the fly) safe to mix with code that needs to make hard decisions — the loop never has to parse or trust the creative part, only the tagged part.

role: z.enum(['planner', 'architect', 'skeptic', ...]) // drives finalization/challenger logic
name: z.string()     // cosmetic only
persona: z.string()  // cosmetic only, becomes the system prompt

Getting a diagram out of an LLM without a rendering library

generate-plan-visual.ts asks the model to respond with "exactly one <svg>...</svg> element and nothing else," then pulls it out with a plain regex (/<svg>[\s\S]*?<\/svg>/i) and drops it straight into the page. No diagramming library, no layout engine, no JSON-then-render step — SVG is just text, and a model that's seen enough of it can write the markup directly, coordinates and all.

The trick that makes this reliable enough to ship is narrowing the request until the output is nearly deterministic: a fixed viewBox range, a closed palette of six hex colors, an exact shadow-offset/gloss recipe, and "if there are 3 tasks, draw 3 steps, not more." Loose instructions ("draw a nice diagram") invite an under-specified, inconsistent result; a tight visual spec turns free-text generation into something you can safely regex out and trust to render. The regex match is also the fallback path — if the model wraps the SVG in prose or markdown fences anyway, extraction still works because it only looks for the tag pair, not an exact-full-string match.

This is also why the visualizer is deliberately outside the round-robin planning loop (see packages/core/CLAUDE.md): it's a one-shot job handed a finalized, immutable input, so there's nothing to debate and no state to carry between turns — just one prompt in, one SVG out.

Two layers of provider fallback: quota tracking vs. failure cooldown

provider-router.ts's selectProvider checks a rate-limit tracker before ever calling a provider — it knows the configured request/day and token/day budgets and refuses to pick a provider it expects to be exhausted. But that's a static model of the world; a free-tier quota can be stricter in practice than what's configured, or a provider can just be down. So generate-for-agent.ts wraps the actual call in a loop: on failure it calls markProviderDown (provider-health.ts) to set a 5-minute in-memory cooldown keyed by providerId:modelId, then retries the next entry in the agent's provider preference list. The next call to selectProvider sees that cooldown via isProviderDown and skips it automatically.

The split matters: the proactive tracker prevents wasting calls on a provider you already know is over budget, while the reactive cooldown handles the failures you can't predict from your own bookkeeping. This is the same shape as a circuit breaker — a failure trips a breaker that stays open for a fixed window, so the system routes around a bad dependency without hammering it, and self-heals once the window elapses. Neither layer alone is enough: proactive-only misses real-world surprises, reactive-only wastes calls discovering limits you already knew about.

Further reading
  • Martin Fowler's "CircuitBreaker" pattern write-up — the classic description of trip/cooldown/retry that this in-memory downUntil map is a minimal version of.

Bridging an HTTP handler into a plain in-process loop

orchestrator/injection-queue.ts and stop-registry.ts solve the same small problem two ways: a running planning session is just a for loop in one Node process, with no event emitter, message channel, or polling hook of its own. But the web server's "inject a message" and "stop" endpoints are separate HTTP requests that need to reach into that loop from outside. Rather than restructure the loop into something event-driven, both files use the simplest thing that works: a module-level Map/Set keyed by conversation id. The HTTP handler writes into it (enqueue, requestStop); the loop reads from it at the top of its next turn (drain, isStopRequested).

This only works because both sides live in the same process and the loop already polls itself once per turn — there's a natural checkpoint to read the mutable state without needing real concurrency primitives. It would break the moment the server and the loop run in separate processes (a worker, a serverless function, multiple server instances behind a load balancer), at which point the same idea needs an actual queue or pub/sub. Recognizing "same process, already has a loop tick" as the condition that makes a module-level `Map` an acceptable shared-state mechanism — rather than reaching for it out of habit — is the actual transferable lesson.

Why round-robin beats a single agent's tool loop

The committee's runPlanningSession deliberately isn't one LLM in a tool-calling loop deciding when to keep going — it's a plain for loop that hands the full transcript to a different agent (with a different system prompt, sometimes a different model) each turn. Watching the real-estate-app planning session run, this showed its value directly: the Architect proposed full user accounts, and it was a genuinely different agent — the Skeptic — that killed it ("forcing signup before any listing exists creates unnecessary friction"), then a third agent (Devil's Advocate) pushed a wild alternative (blockchain-backed listings) that got explicitly rejected rather than silently absorbed into scope.

A single agent looping on its own tool calls tends to talk itself into agreement — each step is generated by the same weights with the same priors, so it rarely surfaces a genuinely different angle on its own. Rotating which model speaks each turn (see rotateProviderOrder in provider-router.ts) compounds this: different providers actually disagree sometimes, which is the whole point of a "skeptic" role having teeth instead of being decorative.

Further reading
  • Anthropic's engineering post "Building Effective Agents" — the section on multi-agent/"orchestrator-workers" patterns is directly about this tradeoff between a single agent's loop and multiple distinct perspectives.

The "sticker" look is just an offset shadow + a gloss ellipse

Redoing the docs illustrations to match a hand-drawn/poster reference style came down to two cheap SVG tricks layered on flat shapes, not more detail:

<!-- 1. hard offset shadow: same shape, shifted, darker, drawn first -->
<rect x="16" y="56" width="120" height="100" rx="16" fill="#3f7cb8"/>
<rect x="10" y="50" width="120" height="100" rx="16" fill="#5b9bd5" stroke="#1a1a1a" stroke-width="5"/>

<!-- 2. gloss highlight: translucent white ellipse, upper-left, drawn last -->
<rect x="18" y="58" width="44" height="18" rx="9" fill="#fff" opacity="0.28" transform="rotate(-18 40 67)"/>

No gradients, no filters, no blur — just z-order and a darker/lighter version of the same fill color. This is the same idea as Material Design's flat "elevation" shadows and the once-trendy "long shadow" flat-design style: depth read from hard color contrast, not soft blur. It's also cheap enough that an LLM can be told the rule (offset-shadow-behind, gloss-highlight-on-top, reuse a small fixed palette) and generate new icons in a consistent style without seeing every prior example — that's exactly what the plan-visualizer agent does now for finalized plans.

Further reading
  • Refactoring UI by Adam Wathan & Steve Schoger — the shadows/depth chapter is the clearest short treatment of "flat but with just enough depth" for people who don't think of themselves as designers.
