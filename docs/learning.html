Two layers of provider fallback: quota tracking vs. failure cooldown

provider-router.ts's selectProvider checks a rate-limit tracker before ever calling a provider — it knows the configured request/day and token/day budgets and refuses to pick a provider it expects to be exhausted. But that's a static model of the world; a free-tier quota can be stricter in practice than what's configured, or a provider can just be down. So generate-for-agent.ts wraps the actual call in a loop: on failure it calls markProviderDown (provider-health.ts) to set a 5-minute in-memory cooldown keyed by providerId:modelId, then retries the next entry in the agent's provider preference list. The next call to selectProvider sees that cooldown via isProviderDown and skips it automatically.

The split matters: the proactive tracker prevents wasting calls on a provider you already know is over budget, while the reactive cooldown handles the failures you can't predict from your own bookkeeping. This is the same shape as a circuit breaker — a failure trips a breaker that stays open for a fixed window, so the system routes around a bad dependency without hammering it, and self-heals once the window elapses. Neither layer alone is enough: proactive-only misses real-world surprises, reactive-only wastes calls discovering limits you already knew about.

Further reading
  • Martin Fowler's "CircuitBreaker" pattern write-up — the classic description of trip/cooldown/retry that this in-memory downUntil map is a minimal version of.

Bridging an HTTP handler into a plain in-process loop

orchestrator/injection-queue.ts and stop-registry.ts solve the same small problem two ways: a running planning session is just a for loop in one Node process, with no event emitter, message channel, or polling hook of its own. But the web server's "inject a message" and "stop" endpoints are separate HTTP requests that need to reach into that loop from outside. Rather than restructure the loop into something event-driven, both files use the simplest thing that works: a module-level Map/Set keyed by conversation id. The HTTP handler writes into it (enqueue, requestStop); the loop reads from it at the top of its next turn (drain, isStopRequested).

This only works because both sides live in the same process and the loop already polls itself once per turn — there's a natural checkpoint to read the mutable state without needing real concurrency primitives. It would break the moment the server and the loop run in separate processes (a worker, a serverless function, multiple server instances behind a load balancer), at which point the same idea needs an actual queue or pub/sub. Recognizing "same process, already has a loop tick" as the condition that makes a module-level `Map` an acceptable shared-state mechanism — rather than reaching for it out of habit — is the actual transferable lesson.

Why round-robin beats a single agent's tool loop

The committee's runPlanningSession deliberately isn't one LLM in a tool-calling loop deciding when to keep going — it's a plain for loop that hands the full transcript to a different agent (with a different system prompt, sometimes a different model) each turn. Watching the real-estate-app planning session run, this showed its value directly: the Architect proposed full user accounts, and it was a genuinely different agent — the Skeptic — that killed it ("forcing signup before any listing exists creates unnecessary friction"), then a third agent (Devil's Advocate) pushed a wild alternative (blockchain-backed listings) that got explicitly rejected rather than silently absorbed into scope.

A single agent looping on its own tool calls tends to talk itself into agreement — each step is generated by the same weights with the same priors, so it rarely surfaces a genuinely different angle on its own. Rotating which model speaks each turn (see rotateProviderOrder in provider-router.ts) compounds this: different providers actually disagree sometimes, which is the whole point of a "skeptic" role having teeth instead of being decorative.

Further reading
  • Anthropic's engineering post "Building Effective Agents" — the section on multi-agent/"orchestrator-workers" patterns is directly about this tradeoff between a single agent's loop and multiple distinct perspectives.

The "sticker" look is just an offset shadow + a gloss ellipse

Redoing the docs illustrations to match a hand-drawn/poster reference style came down to two cheap SVG tricks layered on flat shapes, not more detail:

<!-- 1. hard offset shadow: same shape, shifted, darker, drawn first -->
<rect x="16" y="56" width="120" height="100" rx="16" fill="#3f7cb8"/>
<rect x="10" y="50" width="120" height="100" rx="16" fill="#5b9bd5" stroke="#1a1a1a" stroke-width="5"/>

<!-- 2. gloss highlight: translucent white ellipse, upper-left, drawn last -->
<rect x="18" y="58" width="44" height="18" rx="9" fill="#fff" opacity="0.28" transform="rotate(-18 40 67)"/>

No gradients, no filters, no blur — just z-order and a darker/lighter version of the same fill color. This is the same idea as Material Design's flat "elevation" shadows and the once-trendy "long shadow" flat-design style: depth read from hard color contrast, not soft blur. It's also cheap enough that an LLM can be told the rule (offset-shadow-behind, gloss-highlight-on-top, reuse a small fixed palette) and generate new icons in a consistent style without seeing every prior example — that's exactly what the plan-visualizer agent does now for finalized plans.

Further reading
  • Refactoring UI by Adam Wathan & Steve Schoger — the shadows/depth chapter is the clearest short treatment of "flat but with just enough depth" for people who don't think of themselves as designers.
